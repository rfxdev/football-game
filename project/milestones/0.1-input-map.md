# 0.1 Input Map

**Status:** Ready

Abstract input bindings — a direction and a single action button — with the 8BitDo working and verified against what the device actually reports. Nothing to move yet; this is the layer everything else reads through.

**Notes:**

- **Verify against what the device actually reports, not what it ought to.** Controller mappings lie, and the cost of finding that out later is every input bug being ambiguous between binding and logic. See [Gamepad Input and Steam Deck Parity](../../ways-of-working/gamepad-input-and-steam-deck-parity.md)
- **One action button is a constraint, not a starting point.** Single-button input means every action competes for the same button in some context, which makes the controls table the scarcest resource in the project — see [the gate](../../ways-of-working/spec-chain.md#the-gate). The reference does the whole on-pitch engine on a stick and one button; binding a second one here would quietly spend something that can't be got back
- **Per-device actions: decide here, or defer knowingly.** Two 8BitDo pads are available, so couch co-op input is testable from the start. Actions can be bound per-device or device-agnostically, and retrofitting the former once every system reads through the latter is the expensive order to do it in
- **No automated tests here.** The Input Map is project configuration, not code. A missing binding fails the instant you pick the pad up, and asserting that `Input.get_vector()` clamps or that a deadzone applies is testing Godot rather than this project. Coverage starts at [0.3 Ball Physics Test Suite](0.3-ball-physics-test-suite.md), against the first arithmetic nobody can eyeball
- Scaffolding, so no reference section and no playtest — this exits on working. The shape it's building toward is *Controls* in [Match Mechanics](../../sources/swos/match-mechanics.md)
