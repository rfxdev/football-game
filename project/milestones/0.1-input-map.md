# 0.1 Input Map

**Status:** Ready

Abstract input bindings — a direction and a single action button — with the keyboard and the 8BitDo bound to the same actions, as the [Player Manual](../../docs/manual/player-manual.md#controls)'s Controls tells the player, and the 8BitDo verified against what the device actually reports. Nothing to move yet; these are the actions the per-player intent at [1.1 Movement and Possession](1.1-movement-and-possession.md) reads.

**Notes:**

- **Verify against what the device actually reports, not what it ought to.** Controller mappings lie, and the cost of finding that out later is every input bug being ambiguous between binding and logic. See [Deck Input Parity](../../ways-of-working/deck-input-parity.md)
- **Record the 8BitDo's start-up combination in [Deck Input Parity](../../ways-of-working/deck-input-parity.md#the-dev-controller)**, closing its TODO. This is the milestone that finds it out
- **Bind one action button, not two.** A second binding spends the controls table — see [the gate](../../ways-of-working/spec-chain.md#the-gate)
- **One pad, one player.** Two-player mode is in [Controls](../ideas/controls.md); what keeps it cheap later is the per-player intent in [On-the-Ball Mechanics](../../docs/design/match-engine/on-the-ball-mechanics.md)
- **No automated tests, and nothing earlier for 360 Testing to look back at.** The Input Map is configuration and engine behaviour, which don't earn a test per [Automation Testing](../../ways-of-working/automation-testing.md#what-a-test-has-to-earn). Coverage starts with the first simulation code
- **The wiring is scaffolding; which control does what is *told*.** No design doc and no playtest — this exits when every control in the manual's table works on both devices. The rules it binds to are *Input* in [Architecture and Stack](../../docs/decisions/architecture-and-stack.md), and what reads it is [Input as Intent](../../docs/design/match-engine/on-the-ball-mechanics.md#input-as-intent)
