# 0.1 Input Map

**Status:** Ready

Abstract input bindings — a direction and a single action button — with the 8BitDo working and verified against what the device actually reports. Nothing to move yet; this is the layer everything else reads through.

**Notes:**

- **Verify against what the device actually reports, not what it ought to.** Controller mappings lie, and the cost of finding that out later is every input bug being ambiguous between binding and logic. See [Gamepad Input and Steam Deck Parity](../../ways-of-working/gamepad-input-and-steam-deck-parity.md)
- **Bind one action button, not two.** A second binding spends the controls table — see [the gate](../../ways-of-working/spec-chain.md#the-gate)
- **One pad, one player.** Two-player mode is in [Ideas](../ideas.md); what keeps it cheap later is the per-player intent in [Player Controller and Input](../../docs/design/match-engine/player-controller-and-input.md)
- **No automated tests, and nothing earlier for 360 Testing to look back at.** The Input Map is configuration and engine behaviour, which don't earn a test per [Automation Testing](../../ways-of-working/automation-testing.md#what-a-test-has-to-earn). Coverage starts at [0.3 Ball Physics Test Suite](0.3-ball-physics-test-suite.md)
- Scaffolding, so no design doc and no playtest — this exits on working. The shape it's building toward is *Controls* in [Match Mechanics](../../sources/swos/match-mechanics.md)
